# ADR 002: 不引入 X-Algorithm 推荐系统技术改进 WGMM 预测

## 状态

已采纳 (Accepted)

## 日期

2026-01-21

## 当前实现说明

当前 WGMM 代码已经是小型模块化单体应用：`monitor.py` 是入口壳，业务实现位于 `wgmm_monitor/`。本 ADR 拒绝的是 X-Algorithm 风格的推荐系统技术和 Pipeline 架构，不反对当前这种按职责拆分的轻量模块边界。

## 背景 (Context)

X-Algorithm 和 WGMM 属于不同技术范式。

| 维度 | X-Algorithm | WGMM |
|------|-------------|------|
| 目标 | 从海量候选中筛选个性化内容 | 监控单一 UP 主的视频更新 |
| 核心问题 | 信息检索、排序、推荐 | 周期性发布时间识别 |
| 输入 | 用户特征和候选内容特征 | 历史发布时间戳和空检查历史 |
| 输出 | 个性化推荐列表 | 下一次检查时间 |
| 技术栈 | 深度学习、双塔模型、Transformer、Embedding | 高斯核、周期特征、指数衰减、NumPy |
| 数据规模 | 百万级候选 | 数十到数百条历史 |
| 优化目标 | 推荐相关性 | 监控及时性和请求节省 |

WGMM 的核心价值是监控，而不是把发布时间预测精度最大化：

1. 根据历史模式减少无效网络请求。
2. 发现新内容后及时通知。
3. 7x24 小时稳定运行。

## 决策 (Decision)

不引入 X-Algorithm 的推荐系统技术来改进 WGMM 调频系统。

## 理由 (Rationale)

### 技术范式不匹配

两阶段召回/排序、Embedding、Transformer、多目标预测等技术解决的是推荐系统问题。WGMM 的问题域是小样本周期性时间建模，当前瓶颈主要在 `yt-dlp` I/O，而不是算法计算。

### 数据规模不匹配

WGMM 的历史样本通常是几十到几百条。对这个规模而言，`wgmm_monitor/wgmm/scoring.py` 的 NumPy 向量化计算已经足够快，复杂检索或深度模型没有实际收益。

### 架构收益不匹配

当前模块边界是：

```text
cli/app -> services -> clients/stores/wgmm/utils/models
```

这与推荐系统 Pipeline 不同。X-Algorithm 式 Sources、Filters、Scorers、Selectors 会把一个单目标监控流程拆成过多抽象层，增加理解和测试成本。

### ROI 不成立

| 方案 | 预期收益 | 成本 | 结论 |
|------|----------|------|------|
| 预测准确度度量 | 可观察性提升 | 低 | 可考虑 |
| 配置外部化 | 调参便利 | 中 | 可考虑 |
| Prometheus 指标 | 运维可见性 | 中 | 可考虑 |
| 两阶段预测架构 | 对小样本无明显收益 | 高 | 拒绝 |
| Transformer 时间序列编码 | 过度工程化 | 高 | 拒绝 |
| 推荐系统 Pipeline | 不适配当前业务 | 高 | 拒绝 |
| 多目标预测系统 | 目标不匹配 | 高 | 拒绝 |

## 后果 (Consequences)

正面影响：

- 保持 WGMM 的问题域聚焦。
- 避免把监控工具变成推荐系统。
- 继续使用可解释、可测试的小样本统计方法。
- 当前 `wgmm_monitor/wgmm/` 纯算法层可以独立测试。

负面影响：

- 不引入深度学习模型带来的理论表达能力。
- 不追求推荐系统级别的可扩展抽象。

这些负面影响可接受，因为 WGMM 的瓶颈和目标都不在这些方向。

## 保留的改进方向

- 预测准确度度量：用于监控退化，而不是驱动大架构变更。
- 配置外部化：把部分常量转为可配置项。
- 监控和告警：增加运行指标、连续失败告警等。
- 测试覆盖：继续扩展 `tests/` 中的 unittest。

## 明确拒绝的方向

- X-Algorithm 风格 Pipeline 架构。
- 两阶段召回/排序预测架构。
- Transformer 或深度时间序列模型。
- 多目标推荐式预测。
- 分布式预测集群。
- 为追求理论预测精度而牺牲监控稳定性的复杂特征工程。
